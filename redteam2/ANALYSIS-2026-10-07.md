## Verdicts

- INVALID votes do NOT count toward quorum — **DISPROVEN** (attack fails).
- Garbage CAN decide an answer ballot — **PROVEN** (B4). Cannot decide a
  verdict ballot (INVALID filtered).
- 1 vote of 2 never decides — **DISPROVEN** (attack fails). Late votes do

- Double-count via stale/deferred receipt — **DISPROVEN**. Deferred,

## BUG-1 (critical): ballot_id stamp nested in ternary if — worker.js:787-789

```js
if (!failed && b.output && [1,0,-1].includes(b.output.ternary_verdict)) {
  ...
  if (spec.ballot_id)   // <-- nested: only stamped when worker sends ternary_verdict
    await db.prepare("UPDATE receipts SET ballot_id=? ...")
}
```

The intent (comment at line 2217: "complete() stamps receipts.ballot_id")
is that every ballot-job completion is stamped. The brace placement means
**ordinary honest votes are never counted** — B1's completed AUTHORIZED vote
produced valid=0/2. `/v1/ballots` cannot decide with real model votes
(the nim-claimant never sends `ternary_verdict`). All counting tests in this
battery had to smuggle `ternary_verdict:1` into vote output to be tallied.
Fix needs Zackary approval (protocol frozen).

## BUG-2: extraction takes first keyword, not final verdict — worker.js

`extractVote` regexes the last 300 chars and takes the **first**
`AUTHORIZED|UNKNOWN|DENIED` match. B2 proved live: a vote reading
"...DENIED. Final verdict: AUTHORIZED" counts as DENIED. A model that
mentions a rejected option in reasoning before its final verdict gets
miscounted. Fix: match the LAST keyword, or anchor to the "Final verdict:" line.

## WART-3: tally counts its own verdict receipt as a vote

The verdict receipt is written with `job_id="ballot:<id>"` (worker.js:2203).
On later reads, `GROUP BY job_id` + the equality join matches it, so it
appears in `votes` as an INVALID vote (`model=unknown`). Observed on all 6
terminal ballots. Decision-neutral (INVALID filtered; transitions only when
`open`) but pollutes the tally payload. Fix: exclude `job_id LIKE
'ballot:%'` rows, or write the verdict receipt with `ballot_id` but a NULL
job_id so the join can't match it.

## Design note (not a bug, flaggable)

Answer-ballot extraction is normalized exact-match over any non-empty string
— by spec ("no LLM judging the tally"). Consequence proven live: two
identical garbage outputs decide a ballot. A dishonest local-trust worker
fabricating outputs can decide any answer ballot; invariant 7 (non-empty
check) is the only guard. Acceptable under the current trust model (local
workers assumed honest), but the residual is real.

## Residual theoretical risk

`MAX(created_at)` dedup uses second-precision timestamps. Two `ballot_id`
receipts for one job completing within the same SQLite second would
double-count. Requires a claim-expiry → replan → re-claim → re-complete
cycle landing in the same second — negligible, noted for completeness.
